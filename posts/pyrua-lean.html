로봇은 동작 하나씩 시켜야 더 잘함?

같은 GPT-6 Astra와 같은 로봇 동작을 쓰고도 Python 셀 인터페이스는 성공률을 63.1%에서 71.7%로 올렸음. 공동 성공 사례의 입력 토큰은 65% 줄었지만, 단일 모델·시뮬레이션·완성 인터페이스 비교라는 경계가 남았음.

로봇한테 그릇을 접시에 놓으라고 시킴

보통 에이전트는
카메라로 보고 동작 하나를 고름

그 동작이 끝나면
카메라 세 장과 상태가 돌아오고
모델을 다시 부름

조금 내리고
다시 보고
그릇을 놓고
또 보는 식임

통제하기 쉬워 보이는데
작은 동작마다 모델이
대화 전체와 이미지를 다시 읽어야 함

로봇이 움직인 거리보다
대화 기록이 더 빨리 자람

이번 논문은 중간에
Python 실행기 하나를 끼움

모델이 move_to 하나만 고르는 대신
짧은 코드 셀을 작성함

그 셀 안에서
위치를 찾고
조금 내리고
결과를 확인하고
안 됐으면 다시 시도함

모델은 셀이 끝난 뒤에만 돌아옴
이미지도 코드가 요청한 것만 받음

쉽게 말하면
매 동작마다 새 지시를 받던 로봇에게
짧은 작업 절차를 한 번 맡긴 거임

정확히는
이동·집기 같은 기본 동작을
로봇 프리미티브라고 부름

RPent는 이 기본 동작과
영상·지시에서 행동을 내는 VLA를
한데 묶은 실행 스택임

PyRUA-Lean은 같은 RPent 프리미티브를
지속되는 Python 네임스페이스에서 조합함
셀 실행이 끝나도 변수값이 남는 공간임
조건문과 반복문도 쓸 수 있음

아래 두 번째 그림의 코드 셀을 보셈
도구 호출 네 번이
코드 셀 하나로 바뀜

이 셀은 성공한 뒤
텍스트 다섯 줄만 돌려주고
이미지는 한 장도 안 보냄

코드를 행동으로 쓰는 발상 자체는
이전에도 있었음

2022년 Code as Policies는
언어모델이 로봇 정책 코드를 쓰고
피드백 루프와 NumPy를 조합할 수 있음을 보였음

2024년 ICML의 CodeAct는
JSON 한 덩어리보다
실행 가능한 Python을 행동 공간으로 쓰면
일반 에이전트가 더 유연해진다고 보고함

그리고 2026년 Harness VLA가
동결된 VLA와 고전 로봇 동작을
RPent라는 스택으로 묶음

이번 PyRUA-Lean은
바로 그 RPent 구현을 가져옴

새 로봇 팔을 만든 연구가 아니라
같은 팔과 같은 동작을
어떤 인터페이스로 시킬지 비교한 연구임

비교 조건은 이렇게 맞춤

계획 모델은 둘 다 GPT-6 Astra
reasoning effort도 둘 다 high

로봇 프리미티브도 같고
동결된 VLA도 같음

LIBERO-PRO 200개
RoboTwin 2.0 250개
RoboCasa365 250개

합계 700개 task-seed 쌍임

task-seed 쌍은
과제 하나와 초기 조건 하나의 조합임

각 쌍에서 에이전트당 한 번만 돌림
보통 LLM 호출 한도는 40회
긴 RoboCasa composite만 100회임

에피소드 사이 기억은 없음

각 쌍에서 한 번씩만 돌렸다는 점이 중요함
같은 조건 비교는 맞지만
반복 실행의 들쭉날쭉함은 못 잼

먼저 성공률부터 보면

도구 호출은 63.1%
코드 실행은 71.7%였음

차이는 8.6%포인트임

논문 제목의 상대 개선 14%는
8.6을 63.1로 나눈 상대 개선치
약 13.6%를 반올림한 숫자임

네 묶음 모두 코드 쪽이 높았음

atomic은 짧은 단일 조작
composite는 여러 조작이 이어지는 과제임

LIBERO는 83.0→94.0%
RoboTwin은 60.0→69.2%
RoboCasa atomic은 78.9→86.7%
composite는 34.4→39.4%임

표에서 왼쪽 성공률 칸을 먼저 보고
오른쪽 효율 칸은 모집단이 다르다는 걸 기억하셈

논문 제목의 입력 토큰 65% 감소는
700개 전체 평균이 아님

두 에이전트가 모두 성공한 인스턴스만 모아
성공 에피소드당 평균을 낸 값임

그 안에서 LLM 호출은
17.0회에서 8.7회로 줄었음

입력 토큰은
788k에서 276k
65% 감소임

9월 가격표로 계산한 비용은
$1.63에서 $0.74가 됨

토큰은 2.9배 줄었는데
비용은 2.2배만 줄었음

캐시된 입력 토큰이 더 싸서
토큰 수와 달러가 같은 비율로 안 움직인 거임

실패까지 전부 포함하면 격차는 작아짐
RoboCasa atomic의 추정 비용 차이는
약 1.1배까지 내려감

65%를 전체 운용비 절감으로 읽으면 안 됨

그럼 토큰은 어디서 줄었냐

호출 한 번을 짧게 만든 효과보다
모델을 덜 부른 효과가 더 컸음

LIBERO에서 총 토큰 차이는 4.48배

그 안을 뜯으면
호출 수가 2.55배 적었고
호출당 토큰도 1.76배 적었음

두 배수를 곱하면 4.48배가 됨

아래 그림에서 진한 막대가 호출 수
연한 막대가 호출당 토큰임

RoboCasa atomic에선
코드 쪽 호출 한 번이 오히려 더 컸음

첫 프롬프트 자체도
모든 벤치마크에서 코드 쪽이 큼

큰 Python API 설명을 먼저 줘도
왕복 횟수를 줄여 총량을 아낀 셈임

그럼 그냥 이미지를 덜 보내면 되는 거 아님?

연구진도 그걸 따로 시험함

도구 호출 baseline에서
매 동작 뒤 자동으로 오던 이미지를 끄고
필요할 때만 요청하게 바꿈

LIBERO 성공률이
83.0%에서 68.5%로 떨어짐

세 구성이 모두 성공한 131개에서
총 입력 토큰도 원래 baseline과 비슷했음

관찰을 줄이는 버튼 하나로는
코드 실행의 이득이 재현되지 않았음

코드 에이전트도 눈을 감고 일한 게 아님

700개 에피소드의
Python 셀 11,145개를 세어보니
84%가 이미지를 요청했음

다만 20%는
과제가 아직 안 끝났을 때만 요청함

한 셀엔 평균 2.1개 행동이 들어갔고
도구 방식은 LLM 호출당 0.65개였음

19%는 앞 동작 결과를 보고
다음 동작을 바꿈

14%는 움직임을 반복했고
8%는 VLA를 재시도함

관찰을 없앤 건 아님
코드가 다시 볼 시점을 고른 쪽에 가까움

제일 선명한 장면은
바닥에 떨어진 모카포트임

두 에이전트 모두 들고 가다 떨어뜨림

도구 호출 쪽은
VLA에게 다시 집으라고 네 번 요청하고
call 32에서 종료함

코드 쪽도 바로 잘한 건 아님

뚜껑에서 잡은 여러 측정점으로
포트가 얼마나 기울었는지 계산하려다

수치 형식이 맞지 않아
NumPy의 half precision 선형대수가 실패하고
TypeError가 남

근데 앞 셀의 변수는 살아 있었음

다음 셀에서 점군 형을 바꾸고
평면 맞춤을 다시 실행함

기울기를 구해 포트를 세운 다음
손잡이가 아니라 바닥을 버너 위에 맞춰
call 33에서 성공함

아래 그림 왼쪽 아래의 call 23이 에러
그다음 call 24가 수정 실행임

한 번에 완벽한 코드를 쓴 사례가 아님
실패한 상태를 버리지 않고 이어 고친 사례임

캐비닛 문에서도 비슷한 차이가 남

도구 호출 쪽은
손잡이를 조금 당기고 다시 보는 걸 반복함

호출 한도 40회가 끝났는데
문은 덜 열린 상태였음

코드 쪽은 손잡이 위치 세 개를 찍고
그 세 점을 지나는 원을 맞춤

힌지에 붙은 손잡이는
문이 열릴 때 원호를 따라 움직이기 때문임

힌지를 중심으로 한 회전 궤적을 추정한 뒤
그 호를 따라 당겨 call 34에서 성공함

로봇 프리미티브 목록엔
‘문을 원호로 열기’가 따로 없었음

Python이 중간 계산 공간이 되니까
있는 동작으로 새 궤적을 만든 거임

이 차이가 VLA 없이도 남는지 봄

VLA와 운영 가이드를 빼가며
여러 조건을 다시 돌림

RoboTwin에서 VLA 없이 가이드만 둔 조건은
도구 호출 42.8%
코드 실행 68.8%였음

토큰은 1.03M에서 316k
3.2배 차이였음

이 토큰 평균은
두 에이전트가 모두 성공한 인스턴스에서 잼

근데 표에 이상한 줄도 있음

같은 무 VLA RoboTwin에서
가이드를 지웠더니
도구 호출 성공률이 42.8→60.4%로 오름

설명서를 더 준다고
항상 더 잘하는 건 아니었음

여기서 선을 세게 그어야 함

논문은 GPT-6 Astra 하나만 씀
시뮬레이션만 씀
task-seed당 한 번만 실행함

실물 로봇 성능과
반복 실행 분산은 아직 모름

또 비교한 건
Python 셀 전체 묶음임

여러 동작 조합
지속 상태
선택적 피드백이 같이 바뀜

셋 중 무엇이 성공률을 얼마나 올렸는지
독립적으로 분리하지 못함

실제 소요시간도 안 잼
공용 모델 게이트웨이 지연이 들쭉날쭉해서
호출 수로 대신했음

원문도 이 한계를 분명히 적어둠

코드만 성공한 96개 중
일부는 VLA가 우연히 한 번에 된 경우도 있음

성공 차이를 전부
복구 로직의 공으로 돌릴 수 없음

공개 뒤 일주일 사이
이 논문을 직접 인용한 프리프린트 두 편이 나옴

10월 7일 RobotWorld는
84개 과제와 여러 로봇 몸체로 범위를 넓혀
에이전트가 피드백을 어디서 놓치는지 봄

10월 8일 Embodied Turing Machines는
PyRUA-Lean을 실행 중 셀을 쓰는 방식으로 분류함

모델 호출을 줄이는 방향을
다른 방식으로 밀었음

테스트 때 모델을 아예 부르지 않고
미리 만든 상태 기반 코드를 재사용함

둘 다 이번 논문을 참고문헌에 넣었지만
6~7일 만에 연구가 새로 시작됐다고 볼 수는 없음

확인 가능한 건
후속 공개가 이번 결과를 인용했다는 사실까지임

피인용 2건으로 표시됨
