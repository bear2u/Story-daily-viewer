AI 에이전트개발자 도구벤치마크·2026. 10. 22·8분 읽기

전문가 매뉴얼이 AI 코딩을 망친 경우 나옴

49개 코딩 에이전트 스킬을 565개 과제에 넣어 봤더니 39개는 성공률을 못 올렸고 평균 이득은 +1.2%p였음. 성공률 100% 그대로인데 토큰이 450.8% 늘어난 사례와 오래된 Linkerd 예시가 답을 망친 장면까지 따라감.

SWE-Skills-Bench: Do Agent Skills Actually Help in Real-World Software Engineering?
Tingxu Han · Yi Zhang · Wei Song · Chunrong Fang · Zhenyu Chen · Youcheng Sun · Lijie Hu · 2026 · arXiv:2603.15401v1 · 예비 결과 프리프린트 · 동료평가 채택 미확인 (2026-10-22)
원문 그림과 함께 읽는 17파트 해설 · 판본 및 출처 확인: 2026-10-22

이 글의 흐름

매뉴얼은 자산인가 버그인가스킬은 추론 때 넣는 절차서SWE-bench에서 SkillsBench까지84,192개에서 49개로요구사항과 pytest 판정실제 저장소와 생성 과제평균 +1.2%p의 속내도움도 비용이 다름성공률 100%, 토큰 +450.8%성능을 깎은 세 스킬Linkerd의 오래된 예시앵커링·환각·개념 번짐실무에서 어떻게 볼까단일 모델과 한 스킬 한계실패 307건을 분해한 후속스킬을 고쳐 쓰는 SkillMorph프리프린트 상태와 3줄 요약

코딩 에이전트한테
전문가 절차서를 넣어 줬는데
오히려 정답률이 떨어지면 어떡함?

그 절차서는 자산임
아니면 문맥에 심은 버그임?

이번 논문은 그 질문을
49개 공개 스킬로 시험했음

먼저 여기서 스킬은
새 모델을 학습시키는 게 아님

코딩 규칙, 명령, 예시를 묶은
SKILL.md 같은 절차서임

요구사항이 들어오면
관련 스킬을 골라 문맥에 넣고
코드 작성과 테스트에 쓰게 함

쉽게 말하면 참고 매뉴얼임
정확히는 추론 때 주입하는
구조화된 절차 지식임

근데 스킬 평가는 원래 애매했음

SWE-bench는 실제 GitHub 이슈를
코딩 에이전트가 고치는지 봤지만
스킬 유무는 비교하지 않았음

SkillsBench가 처음으로
스킬 있음과 없음을 짝지었음

다만 이번 논문은
SWE가 84개 중 16개라고 적었음

SkillsBench v1 초록은 전체 86개라
두 원문의 규모 표기가 맞지 않음

이번 팀은 그 질문을
소프트웨어 개발에만 좁혔음

같은 저자 Wei Song은
2025년 MCPGauge에서도
외부 문맥의 도움과 비용을 쟀음

팀은 Nanjing·SCUT·UNSW·MBZUAI임

그래서 공개 스킬 84,192개를
세 단계로 걸렀음

분야가 맞는지 보고
내용이 겹치는 걸 솎고
실험 가능한지 확인함

그 끝에 49개가 남았음
각 스킬마다 실제 저장소를 고정하고
요구사항 약 11개씩을 붙였음

초록과 결과표는 565개 과제임

그런데 아래 Figure 3 상자는
550개라고 적었음
원문 내부 숫자 불일치임

이제 과제 하나를 열어 보셈

고정 커밋의 저장소
Ubuntu 컨테이너
요구사항 문서
선택적인 스킬이 한 묶음임

요구사항의 합격 조건마다
pytest 검증기를 붙였음

판정은 LLM 심사위원이 아니라
실행되는 테스트가 맡았음

그런데 완전한 실제 이슈는 아님

저장소는 실제 공개 프로젝트지만
요구사항은 정해진 프롬프트로 만들었음
검증기도 모델이 작성했음

실행 판정은 결정적이어도
무엇을 과제로 만들었는지는
연구 설계의 영향을 받음

또 논문 안에서 스킬 위치가
프로젝트 루트와 ~/.claude로 갈림

재현할 땐 코드 기준으로
주입 위치부터 확인해야 함

이 조건에서 평균은
스킬 없음 89.8%
스킬 있음 91.0%였음

차이는 +1.2%p임

반면 평균 토큰은
303K에서 335K로 늘었음
증가율은 +10.5%였음

39개 스킬은 성공률 변화가 0이었고
그중 24개는 양쪽 다 100%였음

스킬이 무효인 경우와
시험이 너무 쉬운 경우가 섞여 있음

그 평균 아래가 더 중요함

risk-metrics-calculation은
70%에서 100%로 올랐음

토큰도 778K에서 507K로
34.8% 줄었음

반대로 tdd-workflow는
21.4%에서 28.6%로 올랐지만
토큰은 78.6% 늘었음

성공률만 보면 둘 다 도움임
비용까지 보면 성격이 다름

여기서 제일 이상한 줄이 나옴

service-mesh-observability는
양쪽 모두 성공률 100%였음

그런데 토큰은
133K에서 733K가 됐음
+450.8%임

python-resilience도 100% 대 100%인데
529K에서 119K로 줄었음

같은 0%p라도 하나는 낭비고
하나는 큰 효율 개선임

결과에 비용 내용 추가하면
성공률 표 하나로는 부족하단 뜻임

그러다 세 스킬은
성공률까지 깎았음

springboot-tdd는
80%에서 70%로 내려감

linkerd-patterns는
100%에서 90.9%로 내려가고
토큰도 50.3% 늘었음

django-patterns도
90.9%에서 81.8%로 내려감

스킬은 그냥 무시되지 않았음
잘못 참고돼 실제 답을 망쳤음

그중 Linkerd 장면이 선명함

과제는 gRPC 서비스에
mTLS 신원 검증을 요구했음

mTLS는 통신 양쪽이
서로 신원을 확인하는 방식임

스킬 없이 풀 때는
v1beta3, gRPC,
meshTLS.serviceAccounts를 썼음

스킬 템플릿은 v1beta1과
HTTP/1 예시를 담고 있었음

v1beta1과 v1beta3은
Linkerd 설정 문법의 다른 버전임

에이전트는 가까워 보이는 예시를
그대로 붙잡아 버렸음

이제 방해 과정을 세 단계로 봄

첫째, 오래된 값을 복사함
연구진은 surface anchoring이라 부름

둘째, 존재하지 않는
rules/metricsServers를 지어냄

셋째, 요구하지 않은
NetworkPolicy까지 붙였음

저자 표현으로는
anchoring, hallucination,
concept bleed임

관련 예시라서 더 위험했음
틀린 답을 그럴듯하게 좁혀 줬기 때문임

그래서 논문의 실무 결론은
스킬 많이 넣기가 아님

구체 값이 박힌 긴 템플릿보다
프로젝트에서 다시 확인할
추상 원칙이 안전할 수 있음

그리고 성공률과 함께
토큰 비용을 같이 봐야 함

스킬 선택 전에는
버전, 프레임워크, 범위를 확인하고
적용 뒤에는 테스트로 반증해야 함

이 마지막 세 문장은
결과에서 끌어낸 실무 해석임
논문이 직접 검증한 규칙은 아님

한편 이 결과를 일반 법칙으로
받아들이면 안 됨

실험 에이전트는 Claude Code 하나
모델은 Claude Haiku 4.5 하나였음

다른 모델은 이미 절차를 알 수도 있고
약한 모델은 스킬을 못 쓸 수도 있음

CPU 전용 Ubuntu 24.04였고
각 과제엔 스킬 하나만 미리 놨음

검색, 여러 스킬 조합,
모호한 선택 상황은 시험하지 않았음

그 뒤 후속 연구는
이 빈틈을 파고들었음

8월의 실패 분석은
두 벤치에서 307건을 찾았음
기능 실패 125건
효율 회귀 182건이었음

웹개발 벤치는 네 모델 모두에서
Pass@2가 1.3~4.2% 내려가고
토큰이 72~394% 늘었다고 보고함

Pass@2는 두 번 시도 안에
통과했는지 보는 지표임

둘 다 프리프린트라
확정된 보편 법칙은 아님

반대로 10월의 SkillMorph는
나쁜 스킬을 고쳐 쓰는 쪽으로 감

SWE-Skills-Bench에서
원본 스킬의 pass@3 82.45%를
95.51%로 올렸다고 보고함

pass@3는 세 번 중 한 번이라도
성공한 과제 비율임

이것도 arXiv 프리프린트임

고정 매뉴얼을 믿는 문제에서
실행 흔적으로 매뉴얼을 고치는 문제로
연구 질문이 이동한 셈임

결국 스킬은 설치 파일보다
테스트하고 폐기할 코드에 가까움

그렇게 나온 논문은
2026년 3월 16일 공개된
arXiv v1 프리프린트임

저자도 preliminary results와
work in progress라고 적었음
