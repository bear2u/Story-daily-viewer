사용자 한 줄이 0.03%였던 코딩 에이전트 요청

다섯 코딩 에이전트의 첫 모델 요청 1,886개를 뜯어보니, 고정된 21자 사용자 문장은 최신 요청의 0.02~0.07%였음. 나머지에는 릴리스마다 달라지는 지침과 도구 정의가 붙어 있었음.

instruction stack이라 부름

쉽게 말하면
사용자가 편지를 한 줄 썼는데
에이전트가 업무 지침과 도구 설명을 붙여
모델에게 건네는 구조임

정확히는 두 덩어리임

사용자 프롬프트를 뺀 instruction text와
구조화된 tool definitions임

모델명과 생성 설정,
JSON 문법 자체는 stack에서 뺌

원문은 이 글을 12가지 기능으로 나눴음

이 Claude 예시에서는
system prompt만 보면
stack 대부분을 놓침

Claude 예시의 top-level system field는
9,517자였음

그 뒤에 system message가 또 붙고
도구 정의 20개가 57,346자를 차지함

도구 설명만 instruction text의
2.6배 길이였음

그래서 system prompt만 공개해서는
모델 입력 전체를 재현할 수 없음

이런 차이는 전작에서
이미 비용으로 드러났음

2026년 7월 나온 Qwen Code 연구는
같은 모델을 두고

릴리스만 바꿨음

35개 릴리스를
SWE-bench Verified 50개 과제로 비교함

해결률에는 유의한 상승 추세가 없었음

초기 9개 릴리스 약 391K에서
최신 버전 약 668K로 늘었음

70% 넘게 증가한 값임

그때 모델 앞에 실제로 붙은 글임

그래서 이번 팀은 결과 대신
첫 요청을 직접 잡았음

Claude Code, Codex, Gemini CLI,
Qwen Code, OpenCode를 고름

2026년 8월 25일 이전
npm에 공개된 정식 릴리스
1,911개를 시도함

linux/amd64 컨테이너에서 하나씩 실행함

주 모델로 간 첫 요청 1,886개를 건짐

전체 흐름은 위에서 아래가 아니라
왼쪽에서 오른쪽으로 이어짐

1,886개 요청의 instruction text를
주로 문장 단위 349,404개로 나눔

두 사람이 66개 요청의
12,862개 segment를 따로 분류함

사람끼리 Cohen's κ는 0.75였음

우연히 같은 답을 고른 경우를 뺀
분류 일치도임

둘의 판정 차이는 세 번째 저자가 조정해
기준표로 만들었음

자동 분류에 쓴 GLM 5.3 Flash는
그 기준표와
93.4%, κ 0.92로 일치함

commit·PR 추적에서 검증한 link
798개 중 795개가 맞았음

표 가운데가 agent별 릴리스 수임

이렇게 검증한 최신 첫 요청에서
가장 큰 덩어리는 도구 정의였음

최신 릴리스의 request 전체 중
Claude Code는 77.4%,
Qwen Code는 72.3%,
OpenCode는 63.2%가 도구 정의였음

Codex는 40.5%,
Gemini CLI는 18.9%였음

다섯 agent가 똑같다는 결과가 아님

세 agent에서는
도구 정의가 request 절반을 넘었다는 측정임

다섯 agent에서도 비슷했음

29,387자에서 124,873자였음

21자 고정 프롬프트 비중은
0.02%에서 0.07%였음

모두 0.1% 미만임

근데 여기서 기억할 게 있음

사용자가 긴 요구사항을 쓴 실전 비율이 아님
논문이 일부러 같은 21자를 넣은 비교임

굵은 두 문단에 조건과 결과가 같이 적혀 있음

같은 첫 요청에서
role 이름조차 작성자를 보장하지 않았음

여기서 role은 요청 JSON에 붙는
발화자 칸임

Gemini CLI와 Qwen Code는
user-role message에도 agent text를 넣었음

둘은 때때로 assistant message에
Got it. Thanks for the context!도 넣었음

실제 모델이 말한 문장이 아니었음

user role만 모아 사용자 지침이라 부르면
에이전트가 쓴 글을 사용자에게 돌릴 수 있음

이 첫 요청들을 릴리스 순서로 놓으면
같은 제품 안에서도
stack 크기가 달라졌음

최초 릴리스에서 최신 릴리스까지
Codex는 7.8배,
Qwen Code는 4.5배,
Claude Code는 2.3배가 됐음

Gemini CLI는 1.4배였고
OpenCode는 약 4분의 1 줄었음

다만 Codex 구간에는
TypeScript에서 Rust로의 재작성과
기본 모델 변경도 함께 있음

stack 증가의 원인을
한 가지로 찍은 실험은 아님

위쪽 면적 그래프가 request 크기임

그 릴리스별 변화는
몇몇 버전에 몰렸음

버전 번호처럼 계속 바뀌는 값을 가린
1,867개 전환 중
segment나 tool이 바뀐 건 544개였음

29%임

segment 3,108개를 넣고

부분 수정은 537개였음

조금씩 고치기보다
덩어리를 통째로 넣고 뺀 흔적이 많았음

파란색이 segment·tool이 바뀐 릴리스임

집중된 릴리스 변화 중에는
하루짜리도 있었음

도구 정의 18개를 ToolSearch 하나로 바꿈

request가 77,601자에서
20,380자로 줄었음

필요할 때 도구를 찾게 한 구조임

도구 정의를 다시 복원함

바로 다음 날이었음

도구 목록뿐이 아니었음

commit 저자 표시에도 손댐

어떤 주석도 넣지 말라고 했음

나중에는 주변 코드의
주석 밀도를 맞추라고 바뀜

릴리스 지침이 흔적을 바꿀 수 있음

기록돼 있었나

안전을 든 건 2개,
model behavior를 든 건 13개였음

안전 관련 지침이 안 바뀌었다는 뜻은 아님

개발 기록에서 안전이
명시 이유로 드물었다는 측정임

오른쪽 단 맨 아래 안전 막대를 보셈

변경 이유 기록과 별개로
다섯 stack을 서로 비교한 결과도 있음

agent끼리 문장은 달랐음

agent 쌍 10개 중 6개는
30자 이상 같은 segment가 한 번도 없었음

2026년 8월에는
각 agent segment의 95% 이상이
다른 agent에 나타나지 않았음

근데 쓸 수 있는 기능 목록인
capability catalog와
하위 agent에 일을 나누는
subagent delegation은
다섯 agent 모두에 들어옴

같은 문구로 수렴하지 않았어도
비슷한 기능이 각 stack에 나타남

효과나 호환성까지 알 수 없음

저장소 지침과 켜 둔 기능을
함께 기록하라고 권고함

가능하면 실제로 잡아 둔 stack도
보관하라고 적었음
