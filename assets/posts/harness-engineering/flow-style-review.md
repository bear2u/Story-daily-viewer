# 독립 흐름·설명·AI 문체 검토

검토 입력: `report.md`만 읽음. 원장·논문 원문·그림 파일·outline은 읽지 않았음. rubric.md의 흐름·설명 지시와 AI 티 지시, style-guide.md 4절 적용. 원고는 직접 수정하지 않았음. 숫자·날짜·저자·원문 확신 수준의 정확성은 이번 검토의 판단 범위 밖임.

## 결론

25파트의 흐름은 이어짐. 처음의 버그 요청을 하네스의 검색→수정→실행→검증→기억→허용이라는 실제 일로 풀고, 마지막에 같은 모델·버그의 통제된 비교가 남았다는 답으로 돌아옴. 끊김은 없음. 다만 11→12는 지시어가 잘못된 주체를 가리키고, 16→17의 영어 구현 용어는 첫 독자에게 설명이 얕음. 아래 국소 수정을 권고함.

새 용어가 있어도 모두 풀 필요는 없음. 예컨대 apply_patch와 string edit는 앞의 문자열 교체·패치 설명에 기대어 읽을 수 있음. ripgrep는 함수 이름 검색이라는 기능이 바로 붙어 있어 별도 설명이 필요하지 않음. MCP와 skills는 기능 차이를 먼저 풀고 등장해 적절함. ACI·SDK·context compaction·permission/isolation은 설명이 있음.

'확장면'은 한국어 독자에게 모호하므로 '확장 기능을 붙이는 인터페이스' 정도로 풀면 좋음. 'snapshot'은 앞서 '버전 고정'으로 이미 설명했으므로 파트19에서는 '고정한 버전'이라고 하면 충분함. '내부 fork', '동적 import', 'plugin'도 한계 문단의 핵심 범위지만, 일반 독자에게는 '내부에서 갈라져 나온 버전', '실행 중 불러오는 확장 기능'으로 짧게 풀 수 있음. 구현 의미는 원문 대조가 필요함.

괄호로 밀어 넣은 긴 설명 없음. '킬포'·'반전' 같은 밑밥 없는 라벨 없음. '0'의 코드 검색 범위가 기억 검색까지 확장되지 않는다는 예외 설명은 논리적임.

## 기대와 회수

- 도입의 파일 위치·수정 적용·테스트·종료 질문: 파트8·9에서 실행 루프와 종료 검증을 보여 주고 파트24에서 질문에 구체적으로 답함.
- 파트6의 Rombaut 표본 차이 기억하기: 파트13의 Moatless Tools 예외로 회수함.
- 범용 프레임워크 부재 관찰: 파트11에서 SDK/RAG 경계 사례, 파트20에서 양방향 플랫폼 변화로 범위를 지킴.
- 코드 벡터 검색 부재 관찰: 파트13에서 대화 기억과 표본 밖 사례를 붙여 보편적 부재로 읽지 않게 함.
- 최소 루프의 간단함: 파트23에서 90줄 예시의 생략과 증명 없는 성능 추측을 붙여 '짧으니 충분하다'는 기대를 구분함.

회수되지 않은 '기억해두셈' 또는 명시적 예고 없음. 재미 재료는 프레임워크 부재·코드 검색0의 기억 예외·90줄 성능 추측의 무증명이라는 세 가지 이상임. 다만 파트23의 90줄이 뒤늦게 처음 등장하므로 강한 반전이라기보다는 정확히 제한하는 숨은 디테일로 읽힘. 과장해서 재미를 만들지는 않음.

## 마지막 파트

파트24에서 첫 버그 요청으로 돌아와 모델 바깥의 일을 구체적으로 답함. 파트25는 같은 버그와 모델의 통제된 비교라는 다음 작업을 명시하고, 날짜 박힌 현재 공개/심사/후속/재현 확인 수준을 붙임. 3줄 요약이 제목 질문에 연결되며 소스 분석으로 알 수 있는 범위와 아직 안 잰 효과를 구분함. 공식적 기대 문구로 끝내지 않아 좋음.

나머지는 자연스러워 국소 수정 대상으로 잡지 않음. '아래…보셈' 반복은 스킬의 그림 읽기 지시라 AI 티로 세지 않음. 각 파트가 연결어로 시작하지만 앞 명사와 과업을 받아 내용을 진전시키므로 큰 문제 없음. '~아님' 제한 문구가 많아도 기술 관찰의 범위를 구분하는 기능이 있어 일괄 삭제하면 안 됨. 단어 '부재'는 정확한 관찰을 요약하지만 반복될 때 '찾지 못함'으로 풀 수 있음.

전체 인상: 질문→실행 장면→소스의 구현→범위 제한으로 진행해 설명글로 잘 읽힘. 초보에게는 기억 부분의 영어 구현 용어가 가장 가파른 구간임. 그 구간과 한 곳의 잘못된 지시어를 풀면 음슴체 속 문장이 더 자연스럽게 이어짐.
