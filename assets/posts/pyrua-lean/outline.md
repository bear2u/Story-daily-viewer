# 기획서: Fewer Tokens, Better Action

## 판단

- 유형: 해결형 + 예상 밖 결과형
- 독자에게 던질 질문: 로봇에게 매번 “10cm 움직여”라고 새로 말하는 것과, “안 되면 다시 잡고 끝날 때까지 확인해”라는 짧은 프로그램을 한 번 주는 것 중 어느 쪽이 더 잘하고 덜 쓸까?
- 중심 답: 대화형 Python 셀이 LLM 호출 사이의 작은 로컬 제어기 역할을 하면서 연속 동작·조건 확인·재시도를 묶음. 같은 GPT-6 Astra와 같은 로봇 프리미티브에서 성공률이 63.1→71.7%로 올랐고, 둘 다 성공한 인스턴스에선 입력 토큰이 65% 줄었음.
- 반전: 코드는 거의 안 본 게 아님. 셀의 84%가 이미지를 요청했음. 자동 이미지 반환만 끈 baseline은 성공률이 오히려 68.5%로 떨어졌음.
- 가장 중요한 선 긋기: 성공률 +8.6%p(상대 약 14%)는 전체 700개, 토큰 -65%는 둘 다 성공한 부분집합. 단일 모델·시뮬레이션·한 번 실행·완성 인터페이스 비교임.
- 마지막 답: “코드라서 무조건 낫다”가 아니라, 모델이 매 미세 동작마다 왕복하지 않고 로컬 실행기에 중간 판단을 위임할 수 있는 인터페이스가 이 조건에서 유리했음.

## 척추

1. **왕복세**: 도구 호출은 작은 동작 하나마다 모델을 다시 부르고 이미지가 대화에 쌓임.
2. **로컬 제어기**: Python 셀이 여러 프리미티브·조건·재시도를 묶고 필요한 피드백만 돌려줌.
3. **결과**: 성공률과 토큰이 동시에 개선됐지만, 서로 다른 모집단의 수치임.
4. **왜 됐나**: 호출 수 감소가 주원인. 선택적 관찰만으로는 재현 안 됨.
5. **무너질 수 있는 곳**: VLA 확률성, 단일 실행, 시뮬레이션, 구성요소 미분리, 실시간 지연 미측정.

## 밑밥과 회수

- 도입의 “한 번에 프로그램을 맡기면 더 위험하지 않나?” → 모카포트 TypeError를 다음 셀에서 고친 장면으로 회수.
- “토큰 65%” → 둘 다 성공한 부분집합임을 표 직전·직후 두 번 명시.
- “덜 봐서 절약?” → 84% 이미지 요청과 on-demand-only 실패로 반전.
- Code as Policies → CodeAct → Harness VLA 계보 → 후속 공개가 테스트 때 모델 호출을 아예 없애는 방향으로 나아감.

## 재미 재료

- 제목의 14%는 상대값, 표의 실제 차이는 +8.6%p.
- 코드 첫 프롬프트는 오히려 더 큼.
- 셀 84%가 이미지를 요청함. “안 본다”가 아니라 “언제 볼지 고른다”임.
- 모카포트 평면 맞춤이 half precision TypeError로 한 번 터졌는데, 상태가 남아 형변환 후 이어서 성공.
- 가이드를 지웠더니 한 baseline 조건 성공률이 42.8→60.4로 오름.
- 캐시 가격 때문에 토큰 2.9배 감소가 비용에선 2.2배로 줄어듦.

## 뺀 주장

- “코드가 원인”이라는 단일 인과: 세 요소를 분리하지 않음.
- “실시간으로 더 빠름”: wall-clock latency 미측정.
- “실물 로봇에서도 됨”: 이번 실험은 시뮬레이션뿐.
- “후속 연구가 이번 결과를 재현”: 직접 인용은 확인했지만 재현 연구는 아님.
- 변동이 큰 GitHub 별·SNS 반응 수.
